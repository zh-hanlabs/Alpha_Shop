## 1. 30 秒开场（电梯演讲）

一个**对话式电商交易 Agent**：用户用自然语言完成「查—问—办」全流程，调用链路由模型运行时决策（ReAct），而不是代码写死。

它和普通「套壳 ChatBot」的本质区别：LLM 不可靠——会重试、会重放、会传错参数。我把高并发交易系统的工程思维（**幂等 / 分布式锁 / 限流**）迁移到 LLM Agent 的工具层，**正确性不依赖模型的自觉，闸序写在代码里**。每个关键取舍都有混沌测试实测证据（同键 ×10 并发仅 1 单落库、异键 ×50 零超卖、Redis 停机交易 fail-closed），压测数字有客户端/服务端双源对账。

一句话记忆点：**「安全边界必须在代码，不在 Prompt」**。

第二记忆点（数字弹药，W7 实测）：**热缓存较冷回源 QPS 提升 10.2 倍、限流全局桶 10/s 精确放行（同形突发 300 请求拒绝率 96.67%）、真 DeepSeek 首 token P50=735ms 而链路自身开销 <6%**——每个数字都能讲清「怎么测的、口径是什么、瓶颈在哪」。

## 3. 总体框架：五层架构 + 横切层

```
前端(static/index.html) → 接入层(controller) → Agent编排层(agent/ShopAgentGraph)
    → 工具层(tools) → 业务层(service) → H2 / MySQL
                ↘ 横切能力(infra/)：幂等·锁·审计·缓存·RAG·限流·熔断·降级·观测·记忆
```

| 层 | 包 | 职责 | 铁律 |
|---|---|---|---|
| 前端 | `resources/static/index.html` | SSE 消费、打字机、工具状态展示 | 零 Node 构建，一个文件 |
| 接入层 | `controller/` | SSE 五类事件组装（thinking/tool/answer/error/done）、userId 注入 ToolContext、入口限流 | 不含业务逻辑 |
| Agent 层 | `agent/ShopAgentGraph` | 状态图 START→loadMemory→chat→persistMemory→END | token 流走 Sinks 旁路，不穿图 state |
| 工具层 | `tools/query/*`（6 个查询）+ `tools/trade/*`（3 个交易） | 参数白名单校验 + 编排 + 异常消化 | 统一返回 `ToolResult{code,msg,data}`，异常绝不抛给模型 |
| 业务层 | `service/` | 查库、归属校验、状态机、库存扣减 | 返回 null 表示查无 |
| 横切层 | `infra/` | 幂等/锁/审计/缓存/RAG/限流/熔断/降级/观测/记忆仓库 | 独立可测，业务零感知 |

**为什么这样分**：工具是给模型调的「API」，模型可能传幻觉参数（所以工具层必须白名单校验）；业务是给人维护的（所以不能依赖模型行为）；幂等/锁这类横切能力进 `infra/`，通过 `ToolResult` 统一结构无缝插入——交易工具加闸序，调用方（模型侧）零改动。

**两个贯穿全局的安全设计**：

1. **身份注入防越权**：userId 走 ToolContext 注入而非模型参数——模型签名里没有它，用户对话里说「我是 u1002」传不进去。模型伪造不了调用方身份。
2. **「他人订单」与「订单不存在」同话术**（notFound）：若区分二者，攻击者可探测任意订单号是否存在（信息泄露）；不区分则探测无意义。

## 4. 核心业务逻辑：一次对话的旅程

以「订单 10001 到哪了」为例：

```
用户输入
  ↓ POST /api/chat/stream {conversationId, message, userId}
ChatController
  ├─ RateLimitGuard 入口限流：用户桶 2/1s → 全局桶 10/1s（被拒不进图、零 LLM 调用）
  ├─ resolveUserId() → 缺省 u1001（无鉴权，W8+ 换登录态）
  └─ 组装 toolContext = {userId, ToolEventListener(SSE 回调)} 进图
ShopAgentGraph
  ├─ loadMemory：Redis 记忆读（hash+序号，TTL 7 天，fail-open 读失败→空历史照常聊）
  ├─ chat 节点（包 LlmCircuitBreaker）→ 调 LLM（ReAct 循环）
  │    1. 请求 = System Prompt + 记忆窗口历史 + 本轮消息 + 九工具 JSON Schema
  │    2. 模型决策：没给单号？→ 先调 recentOrders 锁定最新订单 → 再调 queryLogistics
  │    3. 工具执行：ToolEvents.publish("🔍 正在查询…") 经旁路 sink 推 SSE
  │    4. ToolResult 回填模型 → 生成自然语言回答（流式逐 token）
  └─ persistMemory：本轮 user/assistant 消息写 Redis
前端按事件渲染：thinking → tool(🔍) → answer(×N 打字机) → done
```

**ReAct 关键认知**：模型看到的只有工具的 JSON Schema（description + 参数说明）和返回的 ToolResult。**工具 description 写得越像需求文档（何时调用/参数含义/空结果怎么办），调用准确率越高**。

**SSE 旁路（W1 的坑，必懂）**：`.stream()` 输出的流里只有 answer 块，工具调用块不进流——「正在查询…」是 controller 创建 `Sinks.Many<ServerSentEvent>`，把「往 sink 塞事件」的 lambda 作为 `ToolEventListener` 放进 toolContext 旁路推送，最后 `Flux.merge` 合流。

**Graph 升级的边界（W5D4 spike 实证）**：SAA Graph 在节点间用序列化器克隆 state——Sinks.Many、带 lambda 的 ToolContext 一进 state 即 `JsonMappingException`。解法：响应式旁路对象走 invocation 持有表（UUID 键），state 只承载可序列化值。图的价值在**编排因果序**（记忆读写节点化），token 流是传输细节，两者正交。附带收益：SSE 断连只取消订阅，图照跑、记忆照落，重发同句由交易幂等闸收束。

## 6. 交易安全三件套（简历核心，W3-W4）

### 6.1 闸序（TradeGuard 统一编排，三交易工具共用）

```
交易工具调用（userId 走 ToolContext 注入）
  → 锁外快查 idempotent:result
      命中 → 审计「重放命中」→ 返回首次结果（不付抢锁开销）
      miss → 抢锁 tryLock(3s)（Redisson RLock，锁键=用户+资源）
          失败 → 「操作处理中」不排队
          成功 → 锁内幂等四态检查
              result 命中 → 返回首次 ToolResult
              mark 占用   → 「操作处理中」（宁可拒绝不可重复）
              全 miss     → 业务执行 @Transactional（原子扣库存/状态机迁移）
                            → 存 result TTL 24h → 审计锁内随写
                            → 运行时异常 → 删 mark（可重试）
          finally 解锁（isHeldByCurrentThread 防误删他人锁）
```

### 6.2 三件套分工（面试必背）

| 组件 | 防什么 | 关键决策（Why） |
|---|---|---|
| 幂等 `infra/idempotent/` | 重放：锁释放后的重试、LLM 同句重发 | 同键返回**首次结果而非报错**——报错触发 LLM 重试死循环，返回结果才让对话自然收束 |
| 分布式锁 `infra/lock/` | 并发双写：SETNX 检查窗口内两笔同时下单 | `tryLock(3s)` 不传 leaseTime → 看门狗续期；抢锁失败不排队；锁粒度 = 用户+资源（下单按商品代位、退款取消按订单） |
| 审计 `infra/audit/` | 事后追溯：谁/何时/哪个幂等键/什么结果 | 双出口埋点（锁内随写 + 重放锁外即写），尽力而为不阻断交易——**审计是物证不是闸门** |

**双保险缺一不可**：只锁不幂等 = 锁释放后的重试穿透；只幂等不锁 = SETNX 检查窗口内双写。

### 6.3 幂等键设计（`IdempotentKeys`，键内容 sha256）

| 动作 | 键组成 | Why |
|---|---|---|
| placeOrder | 用户+动作+商品+数量+**会话+指令摘要** | 下单时订单号还不存在；会话+指令摘要区分「重放」与「新意图」——同会话同句重发=拦，换句话（「再买一个」）或换会话=放行，防误伤正常复购 |
| refund / cancel | 用户+动作+订单号 | 同一订单同一动作只有一个结果，跨会话也拦 |

### 6.4 幂等四态语义（`IdempotentExecutor`）

| 状态 | 表现 | Why |
|---|---|---|
| result 命中 | 返回首次 ToolResult | 重放直接收束，对话不炸 |
| mark 命中无 result | 「操作处理中，请稍后再试」 | 在途或前次崩溃残留——宁可拒绝不可重复 |
| 业务失败（库存不足等） | 确定性结果照存 result | 同句重放返回同结果，不再消耗一次业务执行 |
| 运行时异常 | 删 mark + 返回 error | mark 只为「已开始」负责，瞬时故障可重试 |

### 6.5 混沌测试证据（dev-only 端点绕过 LLM 直打工具层，保证并发确定性）

| 场景 | 攻击方式 | 结果 |
|---|---|---|
| C1 同键重放 ×10 并发 | 同用户/商品/会话/指令摘要同时下单 | **仅 1 单落库**，10 路全返回同一订单号（首次结果），库存精确 -1 |
| C2 异键并发 ×50 | 同会话不同消息（正常复购语义） | **50 单全部落库**、50 个唯一订单号连号，库存 60→9 **零超卖** |
| C3 退款重放 ×10 并发 | 同订单同时发起退款 | 全部返回首次退款结果 ¥59，状态只迁移一次，库存只还一次 |
| C4 Redis 停机 | `docker stop` 期间交易+查询 | 交易 fail-closed「交易暂不可用」；查询（纯 H2）不受影响；恢复后自愈 |
| LLM 层实测 | 10 路并发同句走完整 LLM 链路 | InMemory 记忆竞态使 4/10 拿错商品 id，工具层 notFound 确定性存果、模型自查重搜，**无一错单**——LLM 层的混乱被工具层闸序完全兜住 |

**W7 回归补记**：C1-C7 在 MySQL（W7D1）与 compose 容器化 MySQL（W7D4/D5）上全部重验 PASS——幂等/锁/零超卖语义跨三次数据源切换零漂移。且 C3 首跑「还库存 ×2」钓出一个 H2 时代永远踩不到的真 bug（详见 §9.3）。

## 7. 稳定性三件套（W6）+ 分级降级

护的是 LLM API 这条最贵最脆的外呼链路——**限流挡量、熔断止损、降级保体感、观测留证据**。

| 能力 | 组件 | 挂点 | 要点 |
|---|---|---|---|
| 限流 | `RateLimitGuard`（Redisson RRateLimiter 分布式令牌桶） | ChatController 两端点入口 | 用户桶 2/1s + 全局桶 10/1s，**先用户后全局**（被用户桶拒不消耗全局配额）；fail-open |
| 熔断 | `LlmCircuitBreaker`（Resilience4j programmatic） | chat 节点包整段 LLM 调用 | 滑窗 10 / 失败率 50% / min5 / OPEN 20s / 半开 3 探测；OPEN 抛 CallNotPermittedException 短路 |
| 降级 | `RuleFallbackService`（纯规则话术） | 熔断 OPEN 与 LLM 失败两条路的兜底 | 关键词意图 5 类各配话术；**交易类最先判定且只引导绝不执行**——没有 LLM 就没有二次确认链路，宁可少办不可错办；降级回复分片走 answer 流，打字机体感不变 |
| 观测 | `TurnMetricsRecorder` + `TurnCollector` | 限流轮 controller 记、图内轮收尾记（跨层记账） | 轮级 outcome（OK/RATE_LIMITED/DEGRADED/ERROR）/耗时/首 token/token/工具清单；单行 JSON 日志（W7 JMeter 取数源）+ 环形缓冲 100 |

**为什么限流分布式而熔断进程内**：限流是**共享资源语义**（账号配额/用户公平性），多实例下单用户桶配额会 ×N 放大（Resilience4j RateLimiter 是进程内实现，因此被推翻），状态必须放 Redis；熔断是**实例自保**——各实例独立探测独立降级，半开探测流量可控，进程内反而简单。同一个「保护 LLM」问题，按语义选位置。双实例演证实证：跨实例记忆连续（A 存 B recall）+ 全局桶跨实例共享（12 用户精确 10 过 2 拒、429 分落两实例）。

### 分级降级矩阵（同一个 Redis，两种恢复语义）

按业务代价分级——**交易错一笔是真金白银，知识答错一句是体验问题**：

| 能力 | 停机时行为 | 语义 | 恢复 |
|---|---|---|---|
| 交易 | code 50001「交易暂不可用」拒绝执行 | **fail-closed**（宁可不做不可重复） | 秒级重连自愈 |
| 查询 | 纯 H2 不受影响 | 天然隔离 | — |
| 商品详情 | L1 仍有本地缓存；未命中→透传走库 | **fail-open** | L2 随重连回填 |
| 知识检索 | error「知识库暂不可用」，模型诚实告知，聊天主链路照常 | **fail-open** | 应用重启触发指纹重建 |
| 会话记忆 | 读失败→空历史照常聊；写失败→吞掉仅 warn（粒度=单轮） | **fail-open**（记忆是体验不是正确性） | 重连即恢复 |
| 聊天限流 | Redisson 抛错→放行聊天 | **fail-open**（限流器是保护器不是正确性来源） | 重连即恢复 |

## 8. RAG 与两级缓存（W5）

### RAG 检索分层

| 层 | 实现 | 关键决策（Why） |
|---|---|---|
| 语料 | `knowledge/*.md` 40 条：8 商品×4 + 平台政策 8 | 单条 FAQ=单文档，<500 字整条入索引不做切分（切分策略服务规模） |
| 索引 | `KnowledgeIndexer` 语料全集 sha256 指纹存 Redis，**指纹幂等启动** | 指纹不变跳过（重启零 API 调用）、变更→全量重建、分批 ≤10 条/批、失败不存指纹下次重试、**fail-open 不阻断启动** |
| 向量 | Redis Stack FLAT 索引，DashScope text-embedding-v4 | FLAT 精确 KNN：几十条规模下 HNSW 近似无收益还多一层解释成本 |
| 召回 | top-5 + 相似度阈值 0.5 截断 | 实测定稿：命中分 0.73-0.95，无灰色地带垃圾召回 |
| 重排 | 规则重排 top-3：向量分打底 + 标题整句命中 +0.30 / bigram 命中比例 ×0.10 | 不引 reranker 模型：多一次 API 调用不值；中文无分词，bigram 是最轻量确定性匹配 |
| 注入 | top-3 结构化 data（title/content/source/score…） | 零召回→notFound 引导话术，模型诚实告知不编造 |

**双模型路由两个坑**：SAA 的 embedding 路由键是非标准的 `embedding.text`；且 `spring.ai.model.embedding` 必须显式 `none` 关掉 openai 侧默认装配（各路由条件 matchIfMissing=true），否则容器内出现两个 EmbeddingModel 启动冲突。

### 两级缓存（方案 A：缓存边界=展示字段）

- L1 Caffeine `maximumSize=500, expireAfterWrite=60s`（本地无失效广播，60s=不一致窗口上限）· L2 Redisson RBucket TTL 30min
- 缓存边界 = 商品展示字段（name/description/price/category），**库存永不缓存**——库存是交易正确性字段，每单扣减→每单失效会把命中率打崩（方案 B 被否的原因），stock 永远实时查库
- 读路径 L1→L2→库，回填先 L2 后 L1；L2 故障全部 fail-open；查无商品不缓存负结果
- 一致性 = **Cache Aside 先更库再双删**：先删缓存再更库的窗口内，并发读会把旧值回填并驻留到 TTL（脏数据长期化）；先更库再删缓存最多容忍一个短暂旧值窗口 = 最终一致（dev 端点实测 59.00→66.00→回源新值）

## 9. 压测与部署（W7：把工程能力兑换成简历数字）

### 9.1 压测矩阵（全部有双源对账，证据 `docs/jmeter/w7d2` + `w7d3`）

| 场景 | 形态 | 数字 |
|---|---|---|
| **缓存冷/热（DoD 硬指标②）** | 冷=重启清 L1+仅 DEL 目标 L2 键（严禁 FLUSHDB——幂等键/记忆/索引同库）；热=预热 | 冷 344.8/s（冷窗穿透 P50=160ms，无 singleflight 真 dogpile）→ 热稳态 **3514.9/s ≈ 10.2 倍**；P95 162→23ms ≈ 7 倍；**同 JVM evict 探针隔离**：回源 28ms vs L1 命中 3-4ms（纯缓存贡献 ≈7 倍，冷窗余量是 JIT/连接池预热） |
| **限流关/开（DoD 硬指标①）** | 同形突发 300 请求（10 线程×30） | 限流关 300 全过 vs 限流开**放行 10、429=96.67%**；**全局桶 10/s 精确核验**=突发恰放 10（首秒配额）+ 持续满秒 admit=10；双源对账：服务端 470 RATE_LIMITED = 客户端 470 个 429 |
| 交易异键 ramp-up | 100 线程/10s 爬升/200 单（CSV 专用段） | 0% 错误，库存 500→300 **精确对账零超卖** |
| 交易同键 ×100 | 全新幂等键 100 路并发重放 | 全返首次、仅 1 单（Avg=849ms=锁排队代价，随并发线性：t50=495ms→t100=849ms——正确性的明码标价） |
| 聊天链路吞吐（桩 LLM） | 50 线程×2 | 96.5/s，P50=20ms/P95=45ms，0% 错误 |
| SSE 流式 | PS5 兜底（SSE 插件无 POST body 能力，探路结论） | 30/30 done 收尾，ttfb P50=14ms |
| **真 LLM 小样本** | 真 DeepSeek 16+1 请求 | 首 token P50=**735ms**/P95=1041ms；整轮 P50=**1045ms**/P95=1524ms；**usage 真回传 17/17**（stream-usage 验证收口，prompt≈2494 token/轮=系统提示+记忆窗口的真实成本） |

### 9.2 取数口径（数字可信的原因，面试必讲）

- **双源对账**：客户端=JMeter JTL/HTML；服务端=TurnMetrics 单行 JSON 日志解析（环形缓冲仅 100 轮，压测以日志文件为准）。两组数字逐条吻合（如限流开组服务端 470 RATE_LIMITED = 客户端 470 个 429）。
- **两口径分开陈述**：桩链路吞吐 96.5/s（工程链路能力）≠ 真 LLM 体感 ~1s/轮（生成能力）。**链路自身开销 = totalMs−llmMs <6%**——限流/记忆/Graph/persist 在真 LLM 面前几乎免费，这正是「限流护盾打在真瓶颈之前」的实证。
- **口径陷阱如实声明**：S1 的 getStock 每请求实时查库（缓存只省 detail JSON，12ms 热稳态里有一次 MySQL PK 查询当地板）；CSV 每 JMeter 进程从头读→跨进程重复 userId 命中幂等重放（样本数≠新订单数，按 audit 对账）；usage 桩不回传=N/A+answerChars 代理。
- **踩坑换来的 runbook**：调限流参数必须 `--scan --pattern '*rlimit*'` 全删存量桶（trySetRate 不覆盖活桶+内部键带 hash-tag）；JMeter 遇已存在 JTL 拒绝启动（静默无 summary）。

### 9.3 两个 W7 钓出的真 bug（混沌回归的价值证明，面试讲故事首选）

1. **order_item 缺唯一约束 × 持久化库 init 重跑**：C3 退款回归「还库存 ×2」。逐层排查（幂等审计 10 条同键 code=0、状态机条件迁移只中一次）→ 根因：`order_item` 只有自增主键，MySQL 持久化卷经历两次 init（宿主应用→容器应用）后种子明细翻倍，`continue-on-error` 只兜得住有唯一键的表——**H2 内存库每次启动都是干净库，这个坑 H2 时代永远踩不到**。修复=双平台 schema 补 `uk_order_item_order_product`+存量去重+ALTER，重启后行数稳定实证 init 幂等补齐 5/5 表，C3 复跑 PASS。教训：幂等/锁/状态机全部无辜，是测试夹具被污染；换持久化库必须重审所有 seed 的唯一性。
2. **redis-stack-server 停机不落 RDB**：C5 矩阵 E「恢复后知识事实回归」失败——redis 日志实证 deb 版包装不透传 SIGTERM（最后 BGSAVE 与 stop 间隔 17 分钟且 stop 时无 save），docker stop 后自上次周期 BGSAVE 起的写入全丢（知识索引/幂等标记/会话记忆同窗受损）。修复=compose 显式 `--appendonly yes --save 60 1`（写入跨重启存活实测）；知识索引按设计由应用重启指纹重建兜底。

### 9.4 部署形态（Docker Compose，ADR D8 的落地）

- `docker-compose up -d`：redis-stack（本地镜像 build 禁 pull，deb 不入仓）+ MySQL 8.4（healthcheck 用**带密码 root ping**——防首次 init 的临时 server 误报健康）→ 应用 `dev,mysql` 双 profile（宿主机跑，压测本就打本地）。
- **克隆体验验证**：全新命名卷 → 应用启动 init 自动播种（商品库存回种子值）→ 向量索引按指纹幂等重建（40 条/1.8-2.6s）——一条命令后查/问/办全链路中文零乱码可用。
- app 容器化=加分项：`--profile fullstack` 才启动（零网络 Dockerfile COPY jar），容器内走服务名（SPRING_DATA_REDIS_HOST 宽松绑定）。
- 数据库切换的语义红线：只动连接层，幂等键/锁键/缓存键/观测口径零漂移，C1/C2 跨库回归通过才算切换成功。

## 11. 面试问答预演（按主题分组）

### 交易安全类

| 追问 | 应答要点 |
|---|---|
| 为什么不用数据库唯一索引就够了？ | 唯一索引是最后防线：防不了扣库存/退款这类非唯一键操作；且其报错语义是「异常」而非「返回首次结果」——LLM 收到异常会重试死循环。前置层拦截 + 结果重放语义，还顺带省 DB 压力 |
| 锁超时任务没执行完怎么办？ | `tryLock` 不传 leaseTime，看门狗自动续期直到业务结束；即便锁意外失效，正确性也不靠锁——幂等四态在锁内执行，mark SETNX 只放一个请求进业务。**锁是串行化优化，幂等才是正确性来源** |
| 幂等键怎么防误伤正常复购？ | 键里带会话+指令摘要：同会话同句=重放（拦），换句话或换会话=新意图（放行）。纯参数摘要会把 24h 内复购同商品同数量误判成重复下单 |
| 为什么幂等返回首次结果而不是报错？ | LLM 会根据报错重试，死循环；返回结果才让对话自然收束 |
| 业务失败（库存不足）也存 result？ | 存。确定性结果照存，同句重放返回同结果，不再消耗一次业务执行；只有运行时异常才删 mark 允许重试 |
| 指令摘要的局限？ | 是客户端幂等令牌的近似：同会话隔天一字不差重说仍被拦（误判窗口=TTL 24h）。生产方案是客户端 requestId，本项目用指令摘要近似换取前端零改动 |

### 架构与 Agent 类

| 追问 | 应答要点 |
|---|---|
| 模型「决定调用工具」的依据是什么？ | 工具的 JSON Schema（description+参数说明）；description 写得越像需求文档，调用准确率越高 |
| userId 为什么模型伪造不了？ | 不在工具方法签名里，由 controller 经 ToolContext 注入；对话里说「我是 u1002」只是聊天内容 |
| SSE 流里为什么没有工具调用块？ | `.stream()` 内部工具执行模式只输出 answer 块；「正在查询」事件走 ToolContext 回调旁路 sink 推送，与交易审计埋点同构 |
| 他人订单和不存在为什么必须同话术？ | 防存在性探测：若区分，攻击者可枚举订单号探测哪些真实存在 |
| 为什么 token 流不穿过图状态？ | 图在节点间序列化克隆 state（spike 实证 sink 一进 state 即炸）；图管编排因果序，token 流是传输细节，旁路让两者正交 |
| 工具异常为什么不能抛给模型？ | 模型看到异常会重试，死循环；ToolResult 统一结构 + 工具内消化，还顺带成为幂等闸的插入缝（调用方零改动） |

### 稳定性类

| 追问 | 应答要点 |
|---|---|
| 令牌桶参数怎么定？ | 用户桶 2/1s 按正常聊天节奏定；全局桶 10/1s 按 DeepSeek 账号配额余量+压测余量定；都经冒烟实测回填（10 连发 2 过 8 拒 / 12 用户 10 过 2 拒），不拍脑袋 |
| 为什么熔断进程内而限流分布式？ | 熔断是实例自保（各实例独立探测独立降级，半开探测流量可控）；限流是共享资源语义（账号配额/用户公平性），进程内实现多实例配额 ×N 放大——按语义选位置 |
| 降级为什么是规则回复而不是报错/查询直答？ | 用户体感 > 系统正确性；工具直答没有模型组织语言与安全审查，规则话术是人工审过的安全文本，且交易类只引导绝不执行（没有 LLM 就没有二次确认链路） |
| 为什么知识库 fail-open 而交易 fail-closed？ | 分级降级按业务代价：交易重复执行是真金白银，知识答错一句是体验问题——同一个 Redis，两种恢复语义，矩阵实测 |
| 熔断失败怎么判定？ | LLM 调用抛异常（连接拒绝/超时/5xx/流中断）；工具失败不算——W1 铁律工具内消化不外抛，到不了熔断这层 |

### 缓存与 RAG 类

| 追问 | 应答要点 |
|---|---|
| 为什么 60s 的 L1 TTL 敢叫「一致」？ | 本地缓存无失效广播，TTL=不一致窗口上限；正确性由「先更库再删缓存 + 库存不入缓存」保证：展示字段最多旧 60s 且改价即双删，库存永远实时——**不一致有界且不碰交易正确性** |
| 为什么库存不进缓存？ | 库存是交易正确性字段，每单扣减→每单失效，缓存形同虚设还把命中率打崩；正确性字段零缓存 |
| 为什么不切分知识文档？ | 单条 FAQ <500 字整条入索引，切分策略服务规模；几十条规模下切分是过度设计 |
| 为什么规则重排不上 reranker？ | 多一次 API 调用不值；bigram 对同义改写无感知靠向量分兜底，规模化后 reranker 是第一升级项 |

| B2 | 反驳极限 | 只用数据库唯一索引 + 乐观锁是不是更省事？ | 唯一索引防不了扣库存/退款这类**非唯一键**操作，且它的语义是「抛异常」——LLM 收到异常就重试成死循环。我实际是三层防线：前置幂等+锁（拦重放、省 DB）、DB 状态机条件迁移 + 原子扣减（防超卖）、schema 唯一键（最后一道，W7D5 补 `order_item` uk 才让 init 幂等真正兜住，见 §9.3） |
| B3 限流熔断降级 | 原理 | 限流为什么放 controller 入口而不是图里？ | 被拒不进图 = 零记忆读、零 LLM 调用，配额和外呼成本在闸门外就省掉；放进图里则记忆读写与观测记账已经发生（§4 旅程图第一行）。附带：429 轮单独记 `outcome=RATE_LIMITED`、`totalMs=0`，压测时才能把「被拦」和「处理慢」分开 |
| B3 | 数字口径 | 96.67% 拒绝率的分子分母是什么？ | 同形突发 300 请求（10 线程 ×30）：限流关 300 全过 vs 限流开放行 10、拒绝 290 = 96.67%；**同形对照**让差值全归因于闸。精确性另两重核验：突发恰放 10（=首秒配额）+ 持续组满秒 admit=10；服务端 470 条 RATE_LIMITED 逐条对上客户端 470 个 429（含持续组，`docs/jmeter/w7d3/parse-apprlon.txt`） |
| B3 | 反驳极限 | 熔断期间直接返 503 报错，不是比「伪装成能回答」更诚实？ | 分场景：交易链路宁可少办不可错办，所以降级话术**只引导绝不执行**（没有 LLM 就没有二次确认链路）；查询类降级期确实只能引导稍后再试（已裁定不做工具直答——没有模型组织语言与安全审查）。诚实性靠两点兜住：话术是人工审过的安全文本 + 明说「高峰期」；短路本身瞬时（0.61s 是整轮含约 440ms 打字机分片体感，判据是 `notPermittedCalls` 递增且未发起 TCP 连接） |
| B4 会话记忆 | 原理 | Redis 里为什么用 hash + 序号 field，不用 List 或整窗一个 String？ | 窗口语义 = 整窗替换 + 按序读：hash 一次 `HGETALL` 取全窗，`delete → putAll → expire` 天然对应 `saveAll`；List 做不到「写时刷新整 TTL」的干净语义，整窗 String 每次全量重写是写放大。关键细节：field 是十进制序号，但**读取时按 `Integer.parseInt` 升序重建，不靠 Redis 字典序**（否则 "10" 排在 "2" 前），非数字 field 推尾部——损坏粒度 = 单条，不拖垮整窗（`infra/memory/RedisChatMemoryRepository.java:66-80,153-159`） |
| B4 | 数字口径 | marker_hits=2 到底证明了什么，为什么不直接读 Redis？ | 桩模型让「记忆回来了」变成**行为层可断言事实**：埋 marker → 重启进程 → 新会话 recall，模型回显计数 =2 才算通过（对照 W1 内存态失忆 =1）；直读 Redis 只能证明写进去了，证不了被模型用起来（`docs/resilience/w6d2-memory-smoke.txt`）。跨实例另有一组：A 存 B 取 + 全局桶 12 用户精确 10 过 2 拒且 429 分落两实例（`dual-instance-w6d5.txt`） |
| B4 | 反驳极限 | 为什么不做向量长期记忆（跨会话那种）？ | 记忆（窗口内上下文连续性）与知识（跨会话语义召回）是两件事，按砍单线只做前者——窗口 20 条已覆盖演示链路，做长期召回要再加一套索引与淘汰策略，收益不抵复杂度。演进方向：按 userId 建语义索引做长期召回。存储侧的规模控制已做：TTL 7 天**写时刷新** = 活跃会话永续、沉默会话自动回收，避免无界增长 |
| B5 缓存+压测 | 原理 | 为什么手写 `TwoLevelCache` 而不用 Spring Cache 抽象？ | `@Cacheable` 只管一层；两级要显式控制读序（L1→L2→库）与**回填序（先 L2 后 L1）**、L2 读写删全部 fail-open、以及热点打标（仅 L1 miss 时 INCR）——这些塞进代理会变成讲不清的黑盒。手写还顺带让「查无商品不缓存负结果」这种策略变成一行代码 |
| B5 | 数字口径 | 冷热 10.2 倍里，纯缓存贡献占多少？ | 冷热比混了 JVM 预热与连接池，所以另跑同 JVM evict 探针隔离：回源 28ms vs L1 命中 3-4ms（**纯缓存 ≈7 倍**），冷窗余量归预热。两个口径一起报，并主动交代两个「不利于自己」的事实：S1 的 `getStock` 每请求实时查库（热稳态 12ms 地板里有一次 MySQL PK 查询），冷组是重启清 L1 + 仅 DEL 目标 L2 键（严禁 FLUSHDB——幂等键/记忆/索引同库） |
| B5 | 反驳极限 | 只留 Redis 一层缓存行不行？ | 能跑，但热点商品每请求都付网络往返 + 连接池占用，L1 把这段消掉；代价是本地缓存无失效广播，所以 TTL 只有 60s 当不一致窗口上限，正确性靠「先更库再双删 + 库存永不进缓存」守住。反过来只留 L1 更糟：多实例各持一份、脏窗口不可控。**缓存是加速器不是正确性来源**——这句是整层的设计判据 |

## 12. 已知局限与改进方向（面试主动交代 = 加分）

1. **指令摘要 ≈ 客户端幂等令牌的近似**：同会话隔天一字不差重说仍被拦（误判窗口 = TTL 24h）；生产方案是 requestId 幂等令牌。
2. **userId 由调用方直传无登录态**：换 userId 可绕过用户桶，真解 = 登录态注入，全局桶兜底防打满（压测参数化恰好依赖此口径）。
3. **Redis 单点**：单机 Redisson 无主从/哨兵；fail-closed 是「正确性优先于可用性」的显式取舍，生产需集群化；向量索引与幂等/锁/缓存应分离故障域。
4. **运行时索引丢失不自愈**：W7D5 已在部署层缓解（compose AOF，stop/restart 不再丢数据）；进程内运行时重建（search 命中 No such index 带防抖重建）仍是改进方向。
5. **熔断器进程内**：多实例各自探测各自降级，极端情况实例间状态短暂不一致（设计取舍）。
6. **观测非全链路 trace**：轮级指标为止，跨段靠跨层记账拼齐；不上 Prometheus/Grafana（砍单线）。
7. **降级无查询直答**：纯话术不做工具兜底（已裁定），查询类问题降级期只能引导稍后再试。
8. **审计不在业务事务内**：主交易提交后尽力写，极端情况可能缺记录——物证定位与强一致的取舍。
9. **压测口径**：单机 localhost（无网络抖动/分布式干扰）；HikariCP 起步默认池 10 未调优（数字未受 DB 等待扭曲时不动——不为数字好看预先调参）；真 LLM 小样本 n=17 不做统计显著性声明；压测订单为合成用户（jload*/jsame*）残留于演示库，fixture 重置历史见各证据 md。
