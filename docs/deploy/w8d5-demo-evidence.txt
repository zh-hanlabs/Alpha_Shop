      后主动回答「已处于已退款状态，无需重复申请」，连工具都没调（该轮 toolCalls 只有 OrderQueryTool:1）。
      即：模型自查 → 状态机 40901 → 幂等缓存，三层各自生效（与 W8D2 §11「唯一索引+乐观锁为何不够」同一条线）。

== 步骤 6 锁·并发可视化（Redis 命令级）==
场景 A：12 路并发取消同一订单（就是步骤 3 模型下的那一单 20261005181614965752）
  窗口 356ms，响应分布：x1 {"totalAmount":129.00} + x11 {"totalAmount":129.0}
  → scale 差即身份差：129.00 是首次执行、进程内直接返回；129.0 是 11 次重放从 Redis JSON 缓存读出后反序列化的结果。
  orders → CANCELLED；product 1 库存 42→43（还库存只 +1，不是 +12）；audit 同键 20ce1256… 12 行全 code=0
场景 B：8 路并发取消订单 20261005080948640960，同时 `redis-cli MONITOR` 抓命令（timeout 7s 自停）
  锁相关 EVALSHA 共 30 次 = tryLock 脚本（sha 149c5a8bf186…）22 次 + unlock 脚本（sha 6866459238a1…）8 次；
  hincrby +1/-1 严格成对出现 8 组（8 次进出临界区，无一重叠）：
    "EVALSHA" "149c5a8b…" "1" "lock:trade:u1001:order:20261005080948640960" "30000" "a05ad69b-…:134"
    [lua] "exists" / "hincrby" …:134 "1" / "pexpire" … "30000"        ← 拿到锁：计数 +1、续租 30s
    [lua] "hincrby" …:134 "-1" + "PUBLISH" "redisson_lock__channel:{lock:trade:u1001:order:…}" "0"  ← 释放并唤醒等待者
    非持有者走 "hexists" + "pttl"（不是我的锁 → 读剩余 TTL 决定等多久）
    另有 2 次 "SUBSCRIBE" "redisson_lock__channel:{lock:trade:u1001:order:…}"  ← 真排队（阻塞等 unlock 通知），即压测矩阵 849ms 锁排队那一档的现场版
  幂等读写次数：GET idempotent:result:12db4b41… 共 16 次 = 8 路 × 2（锁外 result 快查 + 锁内二次快查，双检）
                SET idempotent:mark:12db4b41… 1 次 + PSETEX idempotent:result:12db4b41… 1 次 = 业务只执行一次
  orders → CANCELLED；product 7 库存 100→101（+1 而非 +8）；audit 同键 12db4b41… 8 行全 code=0
  响应分布同样呈 x1「59.00」+ x7「59.0」的 scale 分叉
补充口径（诚实记录）：另写了一个 KEYS lock:trade:* 轮询探针想直接抓锁键在场，两次并发窗口（212/356ms）内 0 次命中——
  锁持有时间只有个位数毫秒（一次 DB 事务），轮询要新建 TCP 连接 + KEYS 全库扫，采样粒度太粗。
  因此锁的可视化以 MONITOR 命令流为准（它是 Redis 服务端逐命令记录，不存在采样漏看）。
判定：Redisson 可重入锁（hash 字段=uuid:threadId、lease 30s 看门狗、channel 通知排队者）行为与设计 §2.3 闸序逐条一致；
      N 路并发 → 1 次执行 + (N-1) 次重放 + 库存只动 1 次，三层（锁串行 / 幂等缓存 / 条件更新 status IN(allowedFrom) 防双写）叠加成立。

  锁（MONITOR 命令级可视化：8 组 hincrby +1/-1 严格串行、2 次 SUBSCRIBE 排队、16 次 result GET、1 次 mark SET）
