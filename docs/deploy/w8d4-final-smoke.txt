== 终验判定 ==
README「快速启动」三步（克隆 → docker-compose up -d → 起应用）在**全新卷、全新项目、零改配置**下走通：
  1) 依赖就绪序成立：redis healthy → mysql healthy → app 起来（Started in 4.854s / 重启后 4.821s）
  2) 空库自动播种成立：5 表建成，product 8 / orders 6 / order_item 8（未翻倍）/ logistics 5 / trade_audit_log 0
  3) 向量索引自愈成立：首次构建 40 条 2120ms；重启后指纹匹配跳过重建（AOF 在位）
  4) 查：订单 10001 明细+状态+金额正确（148.90）
  5) 办：下单 ×2 同幂等键 → 同订单号 20261005094540913474、库存只扣 1（200→199）、审计 2 条同键 code=0
  6) 办（退款）：×2 同键 → 同结果、库存只 +1（45→46 / 199→200）、状态 SHIPPED→REFUNDED；
     状态机拒绝层独立生效（10003 待付款、10004 退款中各返 40901 引导话术）
  7) 缓存：重启=冷 53.8ms → 命中 6.8/7.2ms（单请求口径，批量吞吐口径另见压测矩阵）

结论：W8「克隆即跑」终验通过，零代码改动、零新依赖。

########## 附录：终验钓出部署层真 bug（redis AOF 不落卷）##########

== 现象 ==
原堆栈（默认项目 shop_agent）以 docker-compose down + up -d 重建容器后（卷保留，down 无 -v）：
  $ redis-cli DBSIZE      → 0
  $ redis-cli FT.INFO shopagent-knowledge → 无输出（索引不存在）
  redis 日志："Creating AOF base file appendonly.aof.1.base.rdb on server start"（= 起来时卷是空的）

== 定位 ==
$ redis-cli CONFIG GET dir（W7D5 加固后的容器）
dir → /var/lib/redis-stack
$ ls -la /var/lib/redis-stack/appendonlydir   # AOF 全在容器可写层
-rw-r--r-- 1 root root 131 appendonly.aof.1.base.rdb
-rw-r--r-- 1 root root  93 appendonly.aof.1.incr.aof
-rw-r--r-- 1 root root  88 appendonly.aof.manifest
$ ls -la /data                                 # compose 声明的挂载点（卷 shop_agent_redis-data）
total 8  —— 空的，从来没收过盘
根因：deb 版 redis-stack-server 的默认 dir 不是 /data（官方 redis 镜像才是），命令行只加了 --appendonly/--save
没钉 dir，于是 AOF/RDB 全写进容器可写层。W7D5 的「重启写入存活实测」用的是 docker stop/start（同一个容器、同一层），
所以测得过——但它只证明了 stop/start 保得住，没覆盖 down/重建容器这一档。部署文档写的「AOF 持久化」当时并不成立。

== 最小修复（另立 commit，W8 红线允许：终验钓出真 bug）==
compose.yml redis.command 增加 --dir /data 两个参数，把落盘钉在挂载点上；无代码改动、无新依赖。
